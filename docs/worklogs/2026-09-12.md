## 釐清多 Agent 模型選擇的責任邊界

- **使用者需求摘要**：先不實作，確認 App 若要讓不同 Agent 使用不同模型，現有框架是否需要大改，以及 App 是否無法得知 Core 最終選到的模型。
- **解讀與決策**：區分「靜態 per-Agent profile 對應」與「執行期動態路由」。前者已由現有設定與 resolver 支援，不需要改框架；後者若要依任務、租戶、能力、成本或 fallback 動態決策，才需要把 `Resolve(string agentName)` 演進為帶有執行情境的選模請求。模型治理權應留在 App 設定與 Infrastructure policy，Agent 僅聲明角色或能力需求，不直接指定任意供應商模型。
- **實際執行**：檢視 `AgentExecutor`、`ConfiguredAgentModelResolver`、API 註冊與 `appsettings.json` 的實際呼叫鏈；未修改模型程式碼，只新增本次架構討論紀錄。
- **驗證**：確認 Core 以 Agent 邏輯名稱呼叫 `IAgentModelResolver`；Infrastructure 先查 `AgentModels:Agents`，未命中才使用 `DefaultProfile`；App 擁有 profiles 與 mapping 設定，並可透過 `GET /ai/model/{agentName}` 和執行 log 觀察解析結果。因本次沒有程式異動，未重跑 build/test。
- **結果**：目前 `Agents` 為空才使所有角色共用 `local` profile；只要新增 profiles 與 per-Agent mapping，即可在同一次 App 啟動中讓不同 Agent 使用不同 provider/model。現有 API 執行結果尚未攜帶有效模型 metadata，若 UI 需要逐次顯示，可後續擴充 execution result／trace，屬小型 observability 改動。
- **後續**：視產品需求決定是否先加入執行結果的 model descriptor，或設計 `AgentModelRequestContext` 以支援 per-request 動態選模與 runtime reload。
- **回饋摘要**：說明現況並非 Core 隱性決定單一模型；App 是設定與政策的最終擁有者，Infrastructure 負責解析，Core 僅消費解析後模型。

## 評估領域專用 Workflow 與通用平台邊界

- **使用者需求摘要**：討論目前由 Planner、Developer、Reviewer、Fixer 組成的 AgentLab 是否只能處理特定主題，是否應讓 prompt、model context 等由 App 輸入以泛化，以及應立即擴大未來相容性或先完成現有學習目標。
- **解讀與決策**：目前 Agent definitions、typed contracts 與 orchestration 都是軟體開發領域專用，Runtime、Model Provider、Tool／Policy／Observability 等基礎層才是可重用部分。領域專用並非缺陷；固定且可重現的 use case 更適合建立可靠性、eval 與調校基線。現階段採「泛化接縫、不泛化產品」：prompt 應移至可版本化資源，模型與參數保留設定化，執行情境使用 typed context，但不讓 App 傳入任意 system prompt、任意 workflow graph 或未受控 model context。
- **實際執行**：檢視四個 Agent 的硬編碼 prompt、`CodingTask` 資料契約、固定 `AgentWorkflow` 呼叫順序，以及開發藍圖的架構原則、prompt 管理與暫不處理範圍；未修改執行程式碼，只新增本次設計討論紀錄。
- **驗證**：確認目前的 specialization 分布在 Agent prompt、輸入輸出型別與 Workflow state transition，而 model resolver 已具備 provider-neutral 接縫。開發藍圖也已明訂先讓固定 workflow 可觀測、可靠、可評測，再導入 routing／parallel，且 M0–M6 前不優先做 GUI、Marketplace 或通用 plugin 生態。
- **結果**：建議先把 Software Development Workflow 做到可執行、可驗證、可觀測、可評測的尾段，再以第二個真實 workflow 驗證哪些抽象確實可共用。若尚未出現第二個 use case，就先不要建立通用 Agent DSL／Flow 平台。
- **後續**：近期仍依藍圖完成 typed execution result、failure normalization 與 ChangeSet；同時只預留 `PromptId/PromptVersion`、`ModelProfile`、`AgentExecutionContext` 等低成本接縫。第一條 workflow 達成 gate 後，以第二條不同領域或不同 coding flow 做抽象壓力測試，再決定是否抽出 workflow definition／agent catalog。
- **回饋摘要**：說明使用者的判斷沒有錯，但泛化程度需要分層；完整動態 prompt、Agent catalog、workflow graph、租戶政策與 UI 組合起來確實已接近 Agent Flow 平台，不應成為目前學習專案的前置條件。
